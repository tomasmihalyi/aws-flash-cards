# Goal: Self-Maintaining AI-Native Development Flashcard System

> Paste the "GOAL PROMPT" section below as the goal for an autonomous run.
> Sections after it are the binding decisions that run must honour.

## GOAL PROMPT

Build a self-maintaining flashcard system for the AI-native development domain,
deployed on AWS, that keeps itself factually current without a human editing
cards by hand.

Start from `agentcore-flashcards.html` in this repo: a 36KB single-file SPA with
21 hand-authored AgentCore cards. Its `DECK` schema is sound — preserve the
content contract and the flip/filter/keyboard/reduced-motion UX. Convert it from
hardcoded content into a generated deck built from git-versioned card data.

Deliver in phases, each with the exit criteria listed below. Do not proceed to a
later phase until the current one's exit criteria are demonstrably met. Write a
spec under `.kiro/specs/` before writing implementation code.

Non-negotiable rules:
- Numbers, prices, dates and region lists are NEVER generated by a model. They
  are read from deterministic sources and injected.
- No card publishes without a citation to a source that was actually fetched in
  that run (store the source text hash).
- Card retirement and rename are aliasing operations, never deletions.
- Git is the source of truth for card content. The pipeline proposes changes as
  commits (deterministic) or pull requests (judgement-based).

## Decision 1 — Domain boundary (binding)

The deck covers **AI-native development**, not all AWS AI.

### IN scope

- **AgentCore** — all primitives: Runtime, Memory, Gateway, Identity, Code
  Interpreter, Browser, Observability, Policy, Evaluations, Registry, managed
  harness, CLI, payments
- **Bedrock** — models incl. Nova and Anthropic, Guardrails, Knowledge Bases,
  Flows, Data Automation, Evaluations, inference modes and provisioning
- **SageMaker AI** — where developer-relevant: training, inference endpoints,
  Unified Studio, JumpStart
- **Coding agents** — Kiro, Claude Code on Bedrock/AWS, Codex on Bedrock,
  Amazon Q Developer
- **Quick** — Quick Suite and Quick Desktop. Covered for the boundary between
  business-user agentic work and engineer-led development: what Quick is, where
  it stops, when a use case belongs in Quick versus Kiro, and how a Quick-built
  automation hands off to an engineered system. Cards must be usable by a
  developer or an SA advising on that boundary — not Quick end-user how-tos.
- **Frameworks & protocols** — Strands Agents, MCP, A2A
- **Practices & principles** — agentic coding practices, autonomous development
  practices, AI-DLC, spec-driven development, context engineering, cost control
- **Distillations** — blog posts, papers and talks in the above areas, turned
  into consumable cards with attribution

### OUT of scope

Pre-genAI AI/ML services with no developer-agent relevance: Rekognition,
Textract, Comprehend, Transcribe, Polly, Translate, Lex, Personalize, Kendra,
Fraud Detector, Lookout family, Monitron, HealthLake/HealthScribe. Silicon
(Trainium, Inferentia, Neuron) unless it appears in a developer workflow.
Competitor product surfaces, except as references inside positioning cards.

A card is in scope if a developer, or an SA advising developers, would act on it.

## Decision 2 — Retirement and rename flow (binding)

Renames and retirements are part of the self-maintaining loop. Cards are never
silently deleted.

### Card lifecycle field

`preview | ga | deprecated | superseded | retired`

### Identity rules

- Card IDs are stable for the life of the concept and never reused.
- A renamed thing keeps its card and gains an `aka[]` entry with the old name
  and the date it changed.
- A superseded thing sets `superseded_by: <card_id>` and stays reachable.
- A retired card becomes a tombstone: it still resolves on its deep link,
  renders a "this was retired / see X" state, and preserves learner progress.

### Rename detection signals (automated)

1. AWS What's New title language: "now known as", "renamed", "is now",
   "Classic", "end of support", "no longer accepting new customers"
2. Documentation URL redirects (301/302 on a previously-200 doc URL)
3. Disappearance from the Price List API product set
4. `botocore` service-model rename or operation removal
5. Non-AWS changelogs for Claude Code / Codex

### Gate

Detection is automatic. Applying a **rename** is automatic (Tier A, alias +
commit). Applying a **retirement** is human-gated via PR, because a false
retirement silently destroys knowledge.

### Regression fixtures

Both must be handled correctly by the pipeline:
- Bedrock Agents → Bedrock Agents Classic, including the closed-to-new-customers
  date
- QuickSight → Quick Suite lineage, since the Quick family carries a rename in
  its own history

## Content model

Four card kinds, each with its own verification lane:

| kind | source of truth | staleness trigger |
|---|---|---|
| `service-fact` | SSM regions, Price List API, botocore, What's New, docs | source diff |
| `practice` | named document/author, plus `depends_on[]` | dependency fan-out |
| `distillation` | one canonical URL + author + publish date | source edit or dependency fan-out |
| `mental-model` | human-authored | dependency fan-out only |

Required fields on every card, in addition to the existing `DECK` schema:
`card_id`, `kind`, `lifecycle`, `service`, `tags[]`, `aka[]`, `superseded_by`,
`sources[]` (url + fetched_at + content_hash), `verified_at`, `confidence`,
`depends_on[]`.

Split the current `b`/`bt` badge field: `lifecycle` and `kind` are separate
concerns and the existing `ga|pv|core` vocabulary conflates them.

### Dependency fan-out

When a `service-fact` card changes materially, every card listing it in
`depends_on[]` is flagged `needs_review` and queued for judgement. This is the
only mechanism that keeps practice and distillation cards honest, since they
have no deterministic source. Quick-versus-Kiro boundary cards must declare
`depends_on` on both sides, so a capability shift in either product flags the
boundary card for review.

## Provenance tiers

**Tier A — deterministic, no model, auto-commit.** Region availability (SSM
public parameters), pricing (Price List API), API surface (botocore diff),
GA/preview transitions, renames. Written straight to card fields.

**Tier B — model-drafted, grounded, auto-published.** Refresh of an existing
card where the change is small and a specific fetched URL supports it. All
numbers and dates injected from Tier A. Must pass the verifier.

**Tier C — model-drafted, human-gated via PR.** New cards, retirements,
category changes, positioning or "why it matters" claims, anything failing the
verifier. All Quick-versus-Kiro boundary claims are Tier C by definition, since
they are positioning judgements rather than facts.

### Verifier

Decompose each drafted card into atomic claims. Check each against the fetched
source text. Numeric, date and region claims are string-matched, not judged.
Any failure demotes the whole card to Tier C. Maintain ~30 hand-verified cards
as regression fixtures and fail the build if the verifier regresses on them.

## Architecture

Region `ap-southeast-2`. Account to be confirmed before any deploy.

**Read plane** — S3 + CloudFront + OAC. Static SPA plus versioned `deck.json`,
chunked per category. No API, no auth in v1. Single-file HTML remains a build
artifact for offline/field use.

**Write plane** — EventBridge Scheduler → Step Functions:

```
ingest      What's New RSS, AWS blogs, SSM regions, Price List API,
            botocore diff, Anthropic + OpenAI changelogs, nominated blog feeds
fingerprint only reprocess services whose fingerprint changed
classify    route to Tier A / B / C
apply       A: patch + bot-commit
            B: Bedrock draft (schema-constrained) → verifier → commit or demote
            C: open a pull request
fan-out     flag dependent practice/distillation cards
publish     on merge to main: build deck.json + single-file HTML → S3 →
            CloudFront invalidation
```

**AgentCore usage — deliberately narrow.** The deterministic spine stays on Step
Functions and Lambda. One component runs on AgentCore Runtime: the *researcher
agent* that takes an ambiguous launch item, reads documentation, and returns a
card draft with citations. It uses Gateway (docs, pricing, SSM as MCP tools),
Memory (per-service accumulated context), Evaluations (card-quality gate against
the golden set), and Policy (hard rule: cannot publish a card without a verified
citation). Do not move the deterministic pipeline onto AgentCore — that is
over-engineering and the design should say so.

## Frontend requirements at scale

Target 200–400 cards. Required beyond today's UX:

- taxonomy + tag filtering, full-text search
- deep-linkable card URLs (shareable, survive rename via alias)
- spaced repetition (FSRS or SM-2), progress in localStorage, no auth in v1
- tracks: e.g. AgentCore deep dive, agentic coding practices, Quick-vs-Kiro
  positioning, ANZ-relevant
- **"what changed this week"** deck built from git history — hand a returning
  learner only the cards that moved
- per-card provenance display: `verified_at` and source links visible on the
  back face
- fix the a11y defect: both faces are always in the DOM, so screen readers read
  hidden content. Toggle `aria-hidden` on flip.
- icon strategy that scales: icon per service/category, or the official AWS
  Architecture Icons asset package (verify licence terms before shipping)

## Phases and exit criteria

**P0 — Spec.** Requirements, design, tasks under `.kiro/specs/`. Card JSON
schema published and validated. Inclusion policy from Decision 1 committed.
*Exit:* schema validates the 21 existing cards after migration with no data loss.

**P1 — Data-driven build.** Extract cards to JSON, build script renders both
`deck.json` and the single-file HTML. Deck behaviour matches today's file.
*Exit:* existing 21 cards render identically from generated data.

**P2 — Tier A ingest.** SSM regions, Price List, botocore diff wired. Demonstrate
a real card auto-correcting a region or price claim with a provenance record.
*Exit:* one card provably updated end to end with zero model involvement.

**P3 — Deploy read plane.** S3 + CloudFront + OAC, CI publish on merge.
*Exit:* public URL serving the generated deck, cache invalidated on merge.

**P4 — Tier B/C loop.** Bedrock drafting, verifier, PR automation, golden-set
regression. *Exit:* verifier catches an injected hallucination in the fixtures.

**P5 — Rename/retirement + fan-out.** Detection signals, aliasing, tombstones,
dependency fan-out. *Exit:* both rename fixtures handled correctly and a
dependent practice card gets flagged.

**P6 — Content scale-up.** Expand to the full in-scope surface, including the
Quick boundary set. Practice and distillation cards authored from nominated
sources incl. the three published Medium articles on agentic coding.

## Non-goals for v1

No authentication or multi-user backend. No model-generated numbers or dates.
No scraping behind logins or paywalls. No DynamoDB — add it only if sub-daily
Tier A updates without commits become a real requirement. No Quick end-user
how-to content. No attempt to cover AWS AI services outside the Decision 1
boundary.

## Definition of done (v1)

A public CloudFront URL serves a deck of in-scope cards where every factual
claim carries a visible source and verification date; a scheduled pipeline
updates region, pricing and lifecycle facts without human involvement; renames
are applied automatically as aliases; retirements and new cards arrive as pull
requests; and a dependency fan-out flags practice cards when the services they
describe change.
